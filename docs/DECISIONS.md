# Decisions

Choices made where the TRD was silent or unclear. One line each: `date · task · decision · reason`.

| Date | Task | Decision | Reason |
|---|---|---|---|
| 2026-10-22 | T0.1 | `go.mod` replaces go-sdk with `../go-sdk` | `authz` is not tagged yet; T1.4 tags go-sdk and removes the replace |
| 2026-10-22 | T0.1 | `Deps.Authz` is `authz.NewNoOp()` | No module uses it yet; the database-backed authorizer arrives with the admin routes (T5) |
| 2026-10-22 | T0.1 | Newer grpc, otel and x/text in `go.mod` than go-sdk pins | go-sdk's pinned versions fail govulncheck; the remaining findings (stdlib, x/net) need a newer Go toolchain, installed by the developer |
| 2026-10-22 | T1.2 | `authz.New` takes `*Config` instead of `Config` | go-sdk passes large configs by pointer (`sqlkit`, `kafka`, `redis`); the value form fails the `hugeParam` lint |
| 2026-10-22 | T1.2 | Identity source down past 10 × `cache_ttl` returns 503, not 403 | An outage is not a permission decision; `Can` still reports false |
| 2026-10-22 | T1.2 | Scoped roles with the `token` source map through `authz.roles` | A token carries no role → permission map |
| 2026-10-22 | T0.2 | Migration files are named `YYYYMMDDHHMMSS_name.sql` | TRD 3.4 names them this way (the plan's `00001_` examples differ; the TRD wins) |
| 2026-10-22 | T0.2 | goose v3.27.0 through `goose.Provider`, not the global API | v3.28 needs Go 1.26; the Provider avoids package-level state |
| 2026-10-22 | T0.2 | Outbox retry backoff is `2^attempts - 1` seconds from `created_at`, capped at 2^10 s | The TRD 5.2 `outbox` table has no next-attempt column; this needs none |
| 2026-10-22 | T0.2 | Outbox rows stay locked while they are sent, inside the claiming transaction | Guarantees two dispatchers never send one row concurrently without an extra lease column |
| 2026-10-22 | T0.2 | `bootstrap.sql` also creates `pgcrypto` | The `identity` role may lack the privilege to create extensions |
| 2026-10-22 | T0.3 | No `testkit/fixtures.go` yet | There are no business tables to seed; the tasks that add users and roles add their fixtures |
| 2026-10-22 | T0.3 | `testkit.Server` takes an `http.Handler` (`app.Handler()`) | Keeps `internal/platform` free of an `internal/app` import |
| 2026-10-22 | T0.3 | The app owns its Prometheus registry | The global default registry rejects a second app in the same process (tests, mounted mode) |
| 2026-10-22 | T0.4 | `listquery` rejects unknown query keys; endpoints list extra keys in `AllowedParams` | The plan wants an unknown filter to be a 400; the ported parser silently ignored it |
| 2026-10-22 | T0.4 | `listquery` takes `*ListParseConfig` | The added field makes the struct large enough for the `hugeParam` lint |
| 2026-10-22 | T0.4 | A missing or malformed tenant claim is a 401 in `scope.Tenant` | Without a tenant the caller is not authenticated for tenant data; 500 would hide misconfigured tokens |
| 2026-10-22 | T0.5 | One `apierr.New(reason)` with a reason → code table instead of per-status helpers | A reason can never be paired with the wrong status; the table test pins TRD 9.2 |
| 2026-10-22 | T0.5 | `httpx.Handle` wraps go-sdk `handler.Handle` | go-sdk's adapter has no hook for response headers; `Retry-After` comes from `meta.retry_after` |
| 2026-10-23 | T0.6 | chi v5 router instead of `http.ServeMux` | Same as guest-management-be; route groups with their own middleware, and `chi.Walk` for route-list tests |
| 2026-10-23 | T0.6 | 405 envelope uses code `ERR_METHOD_NOT_ALLOWED`, written with an explicit status | errorz has no 405 code; the status is set directly, so the custom code never maps to 500 |
| 2026-10-23 | T0.7 | `internal/` holds `app`, `platform` and `module/<name>`; `platform` keeps its name; no per-audience packages (`admin`, `me`) | A module owns its routes for every audience through `httpx.Routes`, so a feature stays in one package tree |
| 2026-10-23 | T0.7 | An architecture test (`internal/app/arch_test.go`, via `go list`) replaces the depguard module rule | depguard cannot say "any module except its own" in one rule |
| 2026-10-23 | T0.7 | `Register` takes `*httpx.Routes` (TRD 3.5 shows a value) | Five routers make the struct large enough for the `hugeParam` lint, as with `*ListParseConfig` |
| 2026-10-23 | T1.4 | go-identity requires go-sdk `v0.2.0`; the `../go-sdk` replace is gone | go-sdk v0.2.0 ships `authz` |
| 2026-10-23 | T2.1 | Module configuration lives under `modules.<name>`, not an `identity:` block | `TRD 3.2` and Phase 1 SPEC 1.3 already specified it; a setting then sits with the module that reads it, so each `Validate()` is self-contained and only cross-module rules stay in `internal/app`. `TRD 3.1`, `TRD 4` and the plan's T2.1 were updated to match |
| 2026-10-24 | T3.2 | Email encryption keys live in a top-level `crypto:` block, not under `modules.user` | `internal/app` owns the go-sdk crypto adapter behind the `user.EmailCipher` port, so it is the code that reads the keys; `identities.email_at_link` uses the same cipher, so the keys are not one module's |
| 2026-10-24 | T3.2 | Without configured keys, a `local` service derives fixed development keys and warns; staging and production refuse to start | `make run` must work before a developer provisions secrets, and the derived keys are in the source tree, so they are worthless outside local |
| 2026-10-24 | T3.2 | The `EmailCipher` port speaks `[]byte`; the base64 that go-sdk crypto returns stops at the adapter | `email_enc` and `email_hash` are `bytea`; the module should not learn the cipher's text encoding |
| 2026-10-24 | T3.2 | `users` predicates carry no `tenant_id` | A user is a global row in `TRD 5`; membership lives in `tenant_members`, which is where the tenant scope belongs |
| 2026-10-23 | T0.1 | CI runs the newest stable Go (`setup-go` with `go-version: stable`, `check-latest: true`), not the `go 1.26.0` in `go.mod` | govulncheck reports standard-library fixes that only ship in later patch releases; `go.mod` keeps the minimum version |
| 2026-10-24 | T3.1 | The embedded common-password list is SecLists `xato-net-10-million-passwords-10000.txt` | `TRD 10` asks for "the 10k most common passwords" without naming a source. The list the plan's example URL pointed at (`10-million-password-list-top-10000.txt`) no longer exists in SecLists; the xato-net top 10,000 is the same corpus under its current name, 10,000 lines, and case-folds to 9,916 distinct entries |
| 2026-10-24 | T3.1 | `Verify` reports `needsRehash` when **any** stored parameter is below `DefaultParams` | A single weakened cost (memory, passes, parallelism, salt or key length) already makes the hash cheaper to attack, so one comparison per field is both simpler and stricter than comparing a derived cost |
| 2026-10-24 | T3.1 | The policy returns sentinel errors (`ErrTooShort`, `ErrTooLong`, `ErrTooCommon`, `ErrNotUTF8`), not an `apierr` reason | `password` is a leaf package with no HTTP concerns; the sign-in service maps the sentinel onto `PASSWORD_POLICY` and decides what the user is told |
| 2026-10-24 | T3.1 | Non-UTF-8 input is rejected before the length check | A rune count is meaningless over invalid UTF-8, and such a password could never be retyped identically |
| 2026-10-24 | T3.4 | `mail.Message` carries `LinkPath` plus `Token`; the link is built at delivery time, not when queued | Keeps `internal/platform/mail` free of identity paths while still putting the token in the URL fragment; the frontend paths live in `auth/templates` |
| 2026-10-24 | T3.4 | `mail.Sender` clears `payload.token` in the dispatcher's transaction after a successful send | TRD 5 requires a delivered mail row to keep no usable token; a failed send keeps it so the retry can still build the link |
| 2026-10-24 | T3.4 | The worker fails to start in production rather than falling back to a no-op mailer | Only the logging stub exists; a production worker printing one-time tokens to its log, or silently dropping mail, are both worse than refusing to boot |
| 2026-10-24 | T3.4 | `onetime.Consume` returns one `ErrInvalid` for unknown, wrong-purpose and already-used tokens | Distinguishing them would leak whether a link was ever real; expiry is separate because the caller can usefully offer a new link |
| 2026-10-24 | T3.4 | Single use is enforced by `UPDATE ... WHERE used_at IS NULL` and `RowsAffected`, not a row lock | One statement decides the race, so no transaction is needed around `Consume` and the caller keeps control of its own |
| 2026-10-24 | T3.3 | The CLI is `server superadmin reset --email <e>` and `server superadmin transfer --to <e>`, not `server identity superadmin reset` | TRD 7 and the plan disagree on the form. The binary dispatches flat top-level subcommands (`serve`, `worker`, `migrate`); an `identity` level would be the only nested group and adds nothing in a binary that is only identity. TRD 7 should be updated to match |
| 2026-10-24 | T3.3 | The configured super admin password must pass the password policy; a first start with a weak one refuses to boot | The account holds every permission in every tenant. `must_change_password` limits the exposure but the password still signs in once, and the policy is cheap to satisfy in a secret |
| 2026-10-24 | T3.3 | A first start whose super admin email already belongs to an ordinary account refuses to boot instead of promoting it | Promotion would hand the super admin to whoever registered that address first; `superadmin transfer` is the explicit path |
| 2026-10-24 | T3.3 | Bootstrap, reset and transfer take one Postgres transaction-scoped advisory lock (`database.LockXact`) | Pods booting together and a CLI racing a boot run one at a time: the second finds the work done instead of failing on the unique `email_hash` or the one-super-admin index |
| 2026-10-24 | T3.3 | Reset also clears the lockout; transfer revokes the old holder's sessions and gives the new one an active default-tenant membership | A locked-out super admin is the usual reason to reset; the old holder's refresh tokens would otherwise keep minting `sa: true` access tokens |
| 2026-10-24 | T3.3 | The temporary password is `crypto/rand.Text()` (26 base32 characters, 130 bits) | Above the policy minimum, unambiguous to type, and never in a common-password list |
| 2026-10-24 | T3.10 | `GET /v1/auth/config` is made public by a method-scoped rule in `auth.rules`, and the tenancy mode reaches `auth` as a plain `Deps.Tenancy` string set by `internal/app` | `default_protected` is true, so the route needs an explicit rule; scoping it to GET keeps any later method on the path protected. The mode is owned by `modules.tenant`, and a string needs no port |
| 2026-10-24 | T3.5 | Register with `providers.password.enabled: false` answers 404 `PROVIDER_DISABLED`; registration off answers 403 `REGISTRATION_CLOSED`, checked first and before the body is validated | TRD 9.2 defines `PROVIDER_DISABLED` for a provider that is off (named for Google); reusing it is simpler than a new reason, and a closed registration should say so whatever was sent |
| 2026-10-24 | T3.5 | An expired verification token is `TOKEN_INVALID`, like unknown, used and wrong-purpose ones | TRD 9.2 lists expired under `TOKEN_INVALID`; there is no separate reason |
| 2026-10-24 | T3.5 | With `require_email_verification: false`, register creates the account `active` and queues no verification mail | APP_FLOW 16.1 has `register (no verification) -> active` |
| 2026-10-24 | T3.5 | Resend answers 202 for an invalid address too, and sends nothing to a verified or disabled account | Any other answer distinguishes inputs; a disabled account must not be re-activated through a verification link. Malformed JSON stays a 400 (TRD 9.1), added to the spec |
| 2026-10-24 | T3.5 | Multi-mode register into a suspended tenant answers 403 `TENANT_SUSPENDED`; no slug is 400, an unknown slug 404 | TRD 9.4 names 404 for an unknown slug but not the suspended case; `TENANT_SUSPENDED` is the existing reason for joining a suspended tenant |
| 2026-10-24 | T3.5 | Both register paths hash the password before the transaction; a registration that loses the unique-email race queues the existing-account mail in a fresh transaction | Hashing dominates the cost, so the existing-address path takes comparable time (TRD 10 "Enumeration"); the race loser must answer like any existing address |
| 2026-10-24 | T3.5 | `user.Service.Create` and `VerifyEmail` use `database.InTx` (join the caller's transaction) instead of `WithTx` | Registration needs the user, credentials, membership, roles, token, audit and mail in one transaction; `WithTx` refuses to nest |
| 2026-10-24 | T3.6 | The failure that reaches `lockout_after_failures` sets the lock, so with 10 the eleventh attempt is refused with `ACCOUNT_LOCKED`, even with the right password; a wrong password after an expired lock starts the count again from one | APP_FLOW 4 says "lock if >= limit"; carrying the old count over an expired lock would re-lock the account on its first miss |
| 2026-10-24 | T3.6 | A lock is reported (`ACCOUNT_LOCKED`, 401, `meta.retry_after` + `Retry-After`) before the password is checked; pending and disabled accounts (`EMAIL_NOT_VERIFIED`, `ACCOUNT_DISABLED`) only after a correct password | APP_FLOW 4 orders the lock check first and TRD 9.2 defines the locked body; status reasons after the password keep them from enumerating accounts. A locked attempt is not counted or audited as a failure |
| 2026-10-24 | T3.6 | An unknown address and an account without a password both verify against a dummy argon2id hash (current parameters, computed once per process) and answer `INVALID_CREDENTIALS`; neither counts a failure | TRD 10 "Enumeration": same body and similar timing whether or not the account exists |
| 2026-10-24 | T3.6 | Rate limits key on `login:ip:<ip>` and `login:email:<hex blind index>` (and `register:*`, `resend:*` with the same `login_rate_limit` budget, each its own counter); the plain address never reaches the limiter | TRD 10 "Brute force" names login, register and resend; the blind index is keyed, so a Redis dump does not reveal addresses. Forgot/reset limits come with their endpoints |
| 2026-10-24 | T3.6 | The limiter fails open (allows, logs an error) when Redis errors at request time, and the service falls back to in-memory limits when Redis is unreachable at startup | Redis is a soft dependency (TRD 3.3: never a readiness check); the account lockout still bounds password guessing per account |
| 2026-10-24 | T3.6 | Scoped tokens are restricted in `internal/app` by an allow-list `scopedRoutes` (scope -> method + exact path) behind the auth middleware; `password_change` allows only `POST /v1/me/password` and otherwise answers 403 `PASSWORD_CHANGE_REQUIRED`, any other scope a plain 403 | APP_FLOW 9 and TRD 9.2 specify 403 `PASSWORD_CHANGE_REQUIRED`; the password route only has to be mounted, the allow-list already names it |
| 2026-10-24 | T3.6 | The restricted token carries `scope: password_change`, `tid` and `sa` only when relevant, no roles, and lives 10 minutes; its sign-in still resets the counter, stamps `last_sign_in_at` and audits `auth.login` with `restricted: true` | TRD 9.3; the password was proven, so the failure history is cleared, and the token grants nothing but the password change |
| 2026-10-24 | T3.6 | Multi-mode sign-in implements APP_FLOW 5 (named tenant, the only active membership, or `tenant_required` with the active tenants) and refuses a suspended tenant with `TENANT_SUSPENDED` unless the user is the super admin | Only the token-response shapes were in scope; switch-tenant and suspension of existing sessions remain T6.2 |
| 2026-10-24 | T3.6 | `/.well-known/jwks.json` is public through a method-scoped rule in `auth.rules` | With `auth.enabled` the service validates its own tokens through its JWKS URL, and `default_protected: true` would otherwise put the key set itself behind a token |
| 2026-10-24 | T3.7 | Refresh of a disabled user answers 403 `ACCOUNT_DISABLED` (not 401) and revokes the family before returning | TRD 9.4 and APP_FLOW 7 list it under 403; the plan's "401" is looser text and the TRD wins. The rotation's own transaction has committed, and the revocation runs with no transaction open, so it survives the error |
| 2026-10-24 | T3.7 | Refresh by a user with `must_change_password` answers 403 `PASSWORD_CHANGE_REQUIRED` and revokes the family; it does not hand out the restricted token | The restricted token changes the password without the current one (TRD 9.5), and a refresh token never proved the password; APP_FLOW 9 issues it "at sign-in". The user signs in again |
| 2026-10-24 | T3.7 | A refresh whose user lost the active membership of the family's tenant (or whose user or tenant no longer exists) answers 401 `INVALID_CREDENTIALS` and revokes the family; the super admin may refresh in any tenant, suspended included | TRD 9.4 lists `INVALID_CREDENTIALS` for refresh; `NOT_A_MEMBER` is for switch-tenant. Super admin matches sign-in (T3.6); suspension of existing sessions stays T6.2 |
| 2026-10-24 | T3.7 | A token whose family is already revoked is answered like a reuse: 401 `REFRESH_REUSED` and an `auth.refresh_reuse` audit row (`after.rotated` says which case) | APP_FLOW 7 groups "revoked, or rotated longer ago than refresh_reuse_grace" in one branch |
| 2026-10-24 | T3.7 | Logout and logout-all act only on a token that could still refresh (not revoked, not expired, never rotated or rotated inside the grace); any other token, or an unknown one, is a silent 204 with no audit row. A missing `refresh_token` is still a 400 | A stolen token whose family was revoked must not let its holder sign the owner out of every device; the holder of a live token already controls that session. 204 for everything else keeps logout from being an oracle (TRD 9.4 "idempotent") |
| 2026-10-24 | T3.7 | Refresh is rate-limited per IP (`refresh:ip:<ip>`) with its own budget `modules.auth.security.refresh_rate_limit` (default 60/5m), not `login_rate_limit` | TRD 9.4 marks refresh RL; every signed-in client refreshes every 15 minutes and many share a NAT or BFF address, so the 10/5m sign-in budget would lock real users out |
